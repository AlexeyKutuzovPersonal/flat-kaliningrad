# Дашборд по квартирам — общая разметка

Одна страница по одному постоянному адресу. Отметки и заметки видны
отовсюду и переживают потерю или смену машины — вместо файла, который
был единственным носителем разметки до переезда сюда.

```
браузер  ──→  Cloudflare Pages   страница (public/index.html)
             ↕ /api/marks        функция синхронизации
             D1                  отметки, с журналом правок
```

Репозиторий держит **только развёртывание**. Генератор страницы,
выгрузки и данные остались в задаче (`Task - search flat in
Kalningrad`): переносить их сюда значило бы раздвоить библиотеку,
общую с задачей по дому (`tools\lib\review-table.js` — один компонент,
оба дашборда). Схема, функция `/api/marks` и хуки в этом репозитории —
дословная копия того, что уже работает у дома: протокол общий,
специфики квартир в нём нет.

Страница держит четыре таблицы одним компонентом и одной разметкой на
всю страницу (`sl` вторичка, `nb` новостройка, `zk` жилые комплексы,
`dv` застройщики) — метка ставится на объект в любой из них, ключи не
пересекаются.

## Как это устроено

**Отметка привязана к id объекта** вида `источник:https://…` — площадка
плюс ссылка без параметров. Ключ детерминированный, поэтому пересборка
страницы с новыми объектами накопленную разметку не роняет.

**Ключ переживает смену источника-победителя.** Одна и та же квартира
лежит на нескольких площадках; слияние оставляет победителя, а он между
выгрузками меняется — и ключ вместе с ним. Строка поэтому знает и
запасные ключи, по каждой своей ссылке.

**Правки уходят по полям, а не записями.** Человек ставит метку — на
сервер уезжает только цвет. Отсутствие поля в запросе значит «не
трогай», явный `null` — «стёрто». Если отправлять запись целиком, метка
увозит с собой устаревшую копию чужой заметки и молча её затирает.
Проверка `check-sync.js` держит случай под контролем.

**В шапке страницы стоит момент выкладки.** Его ставит хук `pre-commit`
и только тогда, когда в коммит попадает сам `public/index.html`.

**Каждая правка попадает в журнал** (`marks_log`). Пока вход на страницу
не закрыт, ссылка равна праву записи — откатить порчу можно только по
журналу и по ежедневному снимку в `backup/`.

## Первая настройка

Node на этой машине портативный и в PATH его нет, поэтому `npx` не
работает. Все команды wrangler зовутся через обёртку `cf.cmd` из этой
папки — она подставляет нужный node сама.

```bat
cf login
cf d1 create kv-kgd-marks
```

Полученный `database_id` вписать в `wrangler.toml` (сейчас там
плейсхолдер `REPLACE_AFTER_D1_CREATE`), затем:

```bat
cf d1 execute kv-kgd-marks --remote --file=schema.sql
cf pages project create kv-kgd-2b17a94348 --production-branch main
cf pages secret put SYNC_TOKEN
cf pages deploy
```

`SYNC_TOKEN` — содержимое `.sync-token` (файл не коммитится). Он же
вшивается в страницу при сборке, поэтому значения обязаны совпадать.

Отдельно — один раз на каждый клон:

```bat
git config core.hooksPath tools/hooks
```

Эта команда включает **оба** хука, и без неё они не работают вовсе:

- `pre-commit` — проставляет в шапке страницы момент выкладки;
- `pre-push` — публикует страницу на Pages (см. «Обычный цикл» ниже).

Хуки лежат в репозитории, а не в `.git/hooks`, потому что `.git/hooks`
не версионируется. Проверить: `git config core.hooksPath` должен
ответить `tools/hooks`.

## Обычный цикл работы

```bat
rem из папки задачи: пересобрать страницу с данными
node tools\dashboard-shortlist.js

rem проверить перед выкладкой
node ..\tools\check-dashboard.js Rep\public\index.html
cd Rep && node tools\check-sync.js

git add -A && git commit -m "данные на 31 августа" && git push
```

**`git push` и есть выкладка** — её делает хук `pre-push`. Сам по себе
push страницу не публикует: проект Pages создан как direct-upload
(`Git Provider: No` в `cf pages project list`), GitHub к нему не
подключён и пушей не видит. Публикует только `pages deploy`, и хук
зовёт именно её.

Что делает хук:

- срабатывает **только на `main`** и только если менялся
  `public/index.html`;
- выкладывает **до** push; провал выкладки останавливает push;
- после выкладки сверяет, что в продакшне действительно лежит
  запушенный коммит.

Не публиковать этот push: `SKIP_DEPLOY=1 git push`.
Посмотреть, что хук собирается сделать: `DEPLOY_DRY=1 git push`
(push при этом тоже не выполнится).

Проверить руками в любой момент: `cf pages deployment list
--project-name kv-kgd-2b17a94348` — колонка `Source` против `git
rev-parse --short HEAD`.

**Страница ровно одна.** Генератор без флагов пишет прямо сюда, в
`public/index.html`. Отдельный датированный слепок — по-прежнему в
задаче, работает без сервера и без токена, в репозиторий не едет.

## Перенос разметки из локального файла

Существующие метки лежали в `data\marks-live.json` (локальный сервер
`tools\marks-server.js`, который эту площадку до переезда обслуживал)
и в датированных экспортах вида `kaliningrad-marks-*.json`.

```bat
node tools\import-marks.js ..\..\data\marks-live.json --url https://<адрес>/api/marks
node tools\import-marks.js ..\..\data\marks-live.json --url https://<адрес>/api/marks --apply
```

Первая команда — сухой прогон: сколько отметок легло на объекты и
сколько повисло. Повисшие выгружаются в `backup/orphans-<дата>.json` и
при записи сохраняются тоже — объявление может вернуться.

## Проверки

| Команда | Что доказывает |
|---|---|
| `node ..\..\tools\lib\review-table.js` | обвязка таблицы и слой синхронизации, общая с дашбордом дома |
| `node ..\tools\check-dashboard.js Rep\public\index.html` | страница жива в браузере: фильтры, метки, заметки |
| `node tools\check-sync.js` | разметка доезжает между двумя браузерами и переживает перезагрузку у обоих |
| `node tools\stamp-updated.js --self` | разметка отметки выкладки и пересчёт поясов |
| `node tools\backup-marks.js --url …` | снимок разметки в `backup/` |

`check-sync.js` поднимает локальный сервер с локальной базой и ничего
не пишет в боевую разметку. Базу он пересоздаёт целиком.

## Что здесь намеренно неудобно

- **Фильтры и сортировка не сохраняются между людьми.** Персистентность
  (после правки review-table.js для дома, 2026-08-22) — per-browser,
  через `localStorage`: свои у того, кто их поставил, переживают
  перезагрузку у него, но не расползаются на других. Общее — только то,
  что решает человек: метки и заметки.
- **Правку по строке, в которой стоит курсор, человек увидит после того,
  как из неё уйдёт.**
- **Побеждает более поздняя правка** одного и того же поля. Разные поля
  и разные объекты не конфликтуют вовсе.
- **Вход на страницу не закрыт.** Любой, кому попадёт ссылка, может
  править разметку. Защита — неугадываемый адрес, журнал и бэкап.
